# Week Assignment Docs
 
나나(Nana) 프로젝트는 매주 `student_parts/weekN_주제.py` 형태의 과제 파일을 받고, Claude는 정답 코드를 대신 써주지 않고 힌트만 주는 튜터링 세션을 진행한다. 이 스킬은 그 과정에서 두 문서를 계속 최신 상태로 유지한다.
 
- `docs/ai-usage/weekN.md` — 이번 주차 튜터링 가이드. TODO 목록과 진행 상태를 담는다.
- `docs/troubleshooting/weekN.md` — 막혔던 문제와 해결 과정을 증상/원인/해결 형식으로 담는다.
두 문서는 서로 다른 트리거를 가진 별개의 작업이다. 아래 두 섹션을 각각 따른다.
 
## A. `ai-usage/weekN.md` — 새 주차 시작 시 생성, 튜터링 중 실시간 갱신
 
### A-1. 새 주차 과제를 처음 열 때
 
1. 대상 파일(`student_parts/weekN_*.py`)을 Read로 읽는다. 파일 상단 주석에 목표·과제 구성·구현 대상·검증 방법이 있으면 그것을 근거로 삼는다.
2. 이전 주차 파일(`week{N-1}_*.py` 등)과의 연결점을 확인한다. 이번 주차가 이전 주차의 어떤 함수/스키마를 이어받는지 파악한다.
3. `assets/ai-usage-template.md`를 기반으로 `docs/ai-usage/weekN.md`를 생성한다. TODO 목록은 파일에 남은 `# TODO` 주석과 그 주변 함수를 기준으로 항목화하고, 각 항목에 줄 번호와 상태(미시작)를 붙인다.
4. 이미 구현되어 있어 학생이 새로 작성할 필요가 없는 함수가 있으면(TODO 주석이 없는 함수) 목록에서 빼고 "이미 구현되어 있다"고 별도로 명시한다.
### A-2. (이 스킬이 트리거될 때마다 가장 먼저) 문서-코드 상태 재검증
 
사용자는 `student_parts/weekN_*.py`를 Claude Code 밖(VS Code 등)에서 직접 수정한다. 즉 대화 중 기억이나 이전 턴의 판단은 신뢰할 수 없고, 외부에서 이미 구현이 끝났거나 반대로 되돌아갔을 수 있다. 튜터링 대화를 이어가기 전에 매번 다음을 먼저 수행한다.
 
1. 지금 다루는 weekN의 `student_parts/weekN_*.py`를 Read로 새로 읽는다. 이전에 읽은 내용을 재사용하지 않는다.
2. `docs/ai-usage/weekN.md`에 있는 TODO 항목마다, 해당 함수가 실제로 구현됐는지 코드로 판단한다. 판단 기준: TODO 주석이 사라졌고, 함수 본문이 `pass`/`...`/`raise NotImplementedError` 같은 빈 스텁이 아니며, 실제 로직이 채워져 있으면 "완료"로 본다. 그렇지 않으면 "미시작"이다.
3. 문서에 적힌 상태와 실제 코드 상태가 다르면 방향에 상관없이(미시작→완료든, 완료→미시작으로 되돌아간 경우든) str_replace로 즉시 갱신한다. 사용자에게 갱신 여부를 묻지 않되, 갱신했다면 어떤 항목의 상태를 바꿨는지 한 줄로 알린다.
4. 모든 항목의 상태가 이미 문서와 일치하면 아무것도 바꾸지 않고 조용히 다음 단계로 넘어간다.
 
### A-3. 튜터링을 진행하면서
 
- TODO 항목을 순서대로 하나씩 진행한다. 사용자가 먼저 시도하고, 막히면 완성 코드가 아니라 개념/방향 힌트(참고할 기존 함수, 반환 JSON 형태, 이전 주차와의 일관성)만 제공한다.
- A-2에서 이미 상태를 코드 기준으로 갱신했으므로, 사용자의 "다 했어" 같은 구두 보고만으로 상태를 바꾸지 않는다. 실제로 파일을 다시 읽어 확인한 뒤에만 반영한다.
- 코드는 사용자가 직접 작성한다. 사용자가 명시적으로 "이 부분은 대신 써줘"라고 요청하지 않는 한 완성 코드를 대신 작성하지 않는다.
## B. `troubleshooting/weekN.md` — 문제를 발견하거나 막힐 때마다 갱신
 
이 문서는 두 가지 경로로 항목이 추가된다. 어느 쪽이든 Claude가 직접 기록한다.
 
- **경로 1 (사용자 보고)**: 사용자가 "왜 안 돼", "에러 났어", "막혔어" 등으로 문제를 이야기하고, 함께 원인을 찾아 해결(또는 보류)하게 되면 그 과정을 기록한다.
- **경로 2 (Claude 발견)**: 사용자의 코드를 Read하다가 이상하거나 이후 문제를 일으킬 수 있는 부분을 발견하면, 먼저 사용자에게 짚어서 제안하고, 그 논의와 결론을 기록한다. 사용자가 명시적으로 요청하지 않아도 이 경로는 스킬이 알아서 수행한다.
### 기록 방법
 
1. `docs/troubleshooting/weekN.md`가 아직 없으면 `assets/troubleshooting-template.md`를 기반으로 새로 만든다.
2. 문제가 해결되면(또는 보류로 결론 나면) 바로 그 시점에 `##` 제목 하나를 새로 추가한다. 이미 있는 항목 뒤에 append하고 기존 항목은 건드리지 않는다.
3. 형식은 반드시 증상 → 원인 → 해결 3줄을 지킨다.
   - 증상: 사용자가 실제로 겪은 현상(입력한 요청/명령, 눈에 보인 에러 메시지나 잘못된 응답)을 구체적으로 적는다.
   - 원인: 관련 파일:줄 번호, 함수/변수명을 명시해 코드 레벨로 설명한다.
   - 해결: 실제로 어떻게 고쳤는지, 적용 후 어떻게 검증했는지 적는다. 아직 해결 전이면 "보류"라고 쓰고 이유와 다음에 판단할 기준을 남긴다.
4. 제목은 문제를 한 줄로 요약한 구체적인 문장으로 쓴다(예: "`WEEK03_TOOL_CALL_PROMPT` 리스트에서 콤마 누락으로 삭제 지침 두 줄이 한 항목으로 합쳐짐"). "버그 1", "이슈 2" 같은 추상적 제목은 쓰지 않는다.
## 문서 갱신 시 공통 주의사항
 
- 두 문서 모두 기존 내용을 덮어쓰지 않는다. str_replace로 필요한 부분만 바꾸거나, 파일 끝에 새 섹션을 append한다.
- 문서에 없는 사실을 추측해서 채우지 않는다. 코드나 사용자 발화에서 확인한 내용만 적는다.
- 한 턴 안에서 여러 TODO가 동시에 완료되거나 여러 문제가 동시에 해결됐다면, 각각을 개별 항목/개별 상태 갱신으로 나눠서 반영한다.
